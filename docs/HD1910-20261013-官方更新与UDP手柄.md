## 2. 为什么不整体升级到 0.17

- 官方从 0.15.1 到 0.17.1 改了 **153 个文件、两万多行**。kissqy 的底子是 0.15.1，他自己的 padd 相对官方又改了约 700 行（滚轮测试、输入设置、手柄优先级、网页手柄）。整体升级等于把他的适配重做一遍。
- **两边的接口版本号各自往上加，数字对不上**：kissqy 从 37 加到 40，官方从 37 加到 41，同一个数字含义不同。直接套官方 0.17 的手柄代码，会调到 kissqy 的 robotd 没有的接口。

## 3. 做了什么

### 3.1 UDP 手柄

**做法**：官方是另起一个服务 `netpadd`，和 padd 共用一个新拆出来的映射库。kissqy 的 padd 有他自己的按键映射，所以我们没有照搬，而是在 **padd 里加了第二个输入源**。数据报里的按键翻译成和蓝牙手柄一样的按键事件，摇杆、扳机也一样，蓝牙手柄能做的 UDP 手柄都能做，走的是同一份代码。好处是不用新增服务，不用改中控，也不用改安装包。

**怎么用**：
1. 在 `/etc/robot/feetech-ft5/robotd.toml` 里加：
   ```toml
   [netpad]
   enabled = true
   port = 4210       # 官方默认端口，duckctl 默认就发这里
   timeout_ms = 250  # 多久收不到就算断开；必须小于 [safety] deadman_ms（默认 500）
   ```
2. `sudo systemctl restart padd`。日志里看到 `netpad on — reading the pad from UDP` 就是开了。
3. 电脑上装好 [uv](https://docs.astral.sh/uv/)，插上手柄，运行 `uvx duckctl@0.17.1 udp-pad <鸭子IP>`。Windows、macOS、Linux 都行。

**要注意**：
- **开着 UDP 手柄时，蓝牙手柄和中控的网页手柄都不读**，padd 只读一个来源。改回 `enabled = false` 再重启 padd 就恢复。
- **局域网里没有鉴权**：同一网络里谁能发到这个端口，谁就能开鸭子、让它卸力、让它关机。只在信任的网络里、用的时候开。
- `timeout_ms` 写成 0、写得不小于 deadman，或者 `port` 写成 0，新编的 robotd 会拒绝整个配置文件、起不来，和官方一样。
- padd 的 systemd 沙箱原来只放行 `AF_UNIX AF_NETLINK`，收 UDP 要加 `AF_INET`。已经装好的板子用 drop-in 补：`/etc/systemd/system/padd.service.d/zzzz-udp-pad.conf` 写 `[Service]` 和 `RestrictAddressFamilies=AF_INET`。

### 3.2 手柄掉线自动坐下

正在开的手柄（蓝牙或 UDP）消失 **1 秒**后，鸭子叫一声（疑问的叫声），先问 robotd「是不是已经坐着」，不是就发 `sit_toggle` 坐下，被拒绝的话 5 秒内一直重试。手柄回来时打招呼。不到 1 秒的闪断不出声，也不坐。

- `sit_toggle` 就是 D-pad 下默认绑定的那个动作。**上机前先手动按一次 D-pad 下**，确认 HD-1910 上坐得下去。
- 模型没开（站在 HOME、没按第二下 Start）时，robotd 会回「the policy is not driving」，padd 就当作没事可做，鸭子不动。
- 已经坐着时不会去发 `sit_toggle`，否则会把它「站起来」。

## 4. 审核查出来的问题（现象 → 原因 → 怎么办）

改完按约定开了一个 subagent 独立审核，一共 6 轮。下面是每轮查出来、已经修好的问题，审核都用脚本复现过：

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 真机一开 UDP 手柄，padd 起不来，每 5 秒重启一次，蓝牙也不读 | kissqy 安装包实际装的是 `packaging/padd.service`，我只改了 `padd/systemd/padd.service` | 两份都加 `AF_INET`，同步 `packaging/SHA256SUMS` |
| 按着 Select 时 Wi-Fi 卡了一下，恢复后松手，鸭子卸力瘫倒（24 次里 8 次） | 重连时「本来就按着的键」取错了基准：用的是第一次取帧时的状态，而不是重连那一包的 | 改用重连那一包的按键做基准，现在 0/24 |
| robotd 回答慢（超过 250 ms），padd 以为手柄断了，模式全被重置，下一次 Start 又变成「站起来」 | 判断断开时，没先把卡顿期间排队的包读掉 | 先读空，再判断 |
| 卡顿期间你松手走开了，卡顿结束后鸭子还按卡顿前的摇杆走了约 0.7 秒 | 排队的旧包被当成新数据 | 卡顿后读到的包「不可信」：摇杆当居中，等到实时收到包才恢复 |
| 每次正常断开，日志里都多一条假的「主循环卡住」警告 | 卡顿的判断依据选错了（看的是客户端多久没发包，应该看 padd 多久没读 socket） | 改成看「上次把 socket 读空」的时间，假警告 0 条 |
| 卡顿期间按着 Select 离开，卡顿结束后触发关机；按着 X 的话，前滚翻一直续发 | 排队包里「按着」的状态被当真，卡顿的时间也算进了 2 秒长按 | 不可信期间，长按和续发只计时、不触发 |
| 卡顿期间松开再按下 Select，两次短按变成一次关机 | `SelectButton` 的老逻辑：同一拍里「松开 + 按下」时，松开被吞掉。kissqy 和官方的蓝牙路径也是这样写的 | 先算松开（急停），再从当前时刻重新计时 |

另外还修了：几个文件被写成了 Windows 换行（[踩坑记录 · 软件](../踩坑记录.md#软件) 里早有这条，又踩了一次）；文档补了配错 `[netpad]` 的后果；自动坐下时发出的请求不再显示成「你的请求被拒绝」。

## 5. 测试结果（电脑上）

- 单元测试：padd 79/79（新增 UDP、掉线坐下、卡顿等测试），连跑 8 轮都稳定；robotd-params 106/106。
- 端到端：假 robotd 加模拟 duckctl，覆盖 14 项（回包、每秒健康报告、Start 站起、摇杆走、扳机、第二台电脑抢不走、Select 卸力、断开后停发、1 秒后叫一声并坐下、回来打招呼、重连时按着的键不误触发、闪断不出声、垃圾包不影响），14/14。
- 和官方的兼容性：用官方 0.17.1 的解码器（duckctl 用的就是这份代码）去收我们发的回包和健康报告，**没有一包解不开**。
- 官方 `duckctl` 0.17.1 的 Windows 版能在电脑上跑（`uvx duckctl@0.17.1 udp-pad --help`）；它要插着手柄才会发包，所以「电脑 → 鸭子」这一段要上机才能测。
- 板子用的 padd：aarch64，glibc 最高要求 2.30（板子上是 2.41），新增的动态库只有板子本来就有的 `libudev.so.1`。

## 6. 已知限制

- **robotd 回答特别慢的那一拍**：卡顿之前读到的摇杆还会照发一次，robotd 的 deadman 会因此最多再放行 0.5 秒。蓝牙手柄一直就是这样，kissqy 和官方也一样，这次没改。
- UDP 手柄没有摇杆按下（L3/R3），所以 kissqy 的 L3 滑轮起身测试只能用蓝牙手柄。
