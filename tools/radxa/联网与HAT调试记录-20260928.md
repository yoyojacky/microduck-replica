# 2026-09-28：DHCP 修复与 HAT 舵机只读实测

本记录的日期以调试电脑为准；主板系统时间尚未确认同步，不使用其日志时间推断实际日期。

## 联网结论

此前 9 月 20 日镜像配置了 `wpa_supplicant` 无线认证，但默认 netplan 仅匹配有线接口，没有给 `wlan0` 配置 DHCP。修复为新增 `/etc/systemd/network/25-wlan0.network`：

```ini
[Match]
Name=wlan0

[Network]
DHCP=ipv4
```

在本机个人镜像上实测：

- 成功通过 WiFi SSH 登录，主机名为 `radxa-zero3`。
- 系统为 Armbian 26.2.1 Trixie，内核 `6.1.115-vendor-rk35xx`。
- `networkctl status wlan0` 显示 `Network File: /etc/systemd/network/25-wlan0.network`，状态 `routable (configured)` / `online`，取得 DHCPv4 地址和默认路由。
- `systemd-networkd` 和 `wpa_supplicant@wlan0` 为 active；NetworkManager 未启用；`systemctl --failed` 无失败服务。
- 首次检查时启动约 6 分钟，CPU 温度约 56℃。内核日志仍有显示/GPU、以太网及启动阶段 SD 调谐等告警，不能把“能 SSH”当作全部硬件均无问题。

这证明本次修复在当前主板及无线环境中生效。未做多次冷启动和其他路由器兼容测试，不能宣称所有联网问题都已解决。公开 Release 的旧 `.img.xz` 和校验值没有替换，用户仍需按[使用说明](镜像使用说明.md#4-连-wifi)补配置。

## HAT 串口测试

主板 `/dev/ttyS2` 存在，无进程占用；`serial-getty@ttyS2` 和 `serial-getty@ttyFIQ0` 均被 mask。通过 HAT 以 **1,000,000 baud** 进行测试，只允许协议 `PING` / `READ`，没有发送写寄存器、开启扭矩、校准或运动指令。

首次读取：13 颗舵机成功响应；23 号、34 号没有响应。全 ID 扫描和后续复查表明：

- 关节 ID `10–14`、`20–24`、`30–33` 均有响应，共 14 颗。
- 用户确认嘴部已从 34 改为 29，因此 34 不响应是预期；29 仅识别到固件/型号字段后即停止进一步测试。
- 23 号左膝存在间歇无应答，不能按首次扫描结果认定损坏或未接线。

连续 20 轮对上述 14 颗关节舵机逐个读取反馈寄存器 `56–70`：

| 对象 | 成功 / 次数 | 观察 |
|---|---|---|
| 23 号左膝 | 18 / 20 | 2 次没有收到帧头，成功响应的状态码为 0 |
| 其余 13 颗关节舵机 | 各 20 / 20 | 状态码均为 0，无校验错误或 ID 错误 |

读取期间电压约 7.4–7.5V，温度约 30–33℃。寄存器快照中，14 颗关节舵机扭矩开关均为 0，状态位为 0，运行模式为 4。这里是短时只读通讯检查，不是带载或运动稳定性测试。

## 运动前待处理

1. **23 号的间歇通讯问题。** 先正常关机并断开 HAT 输入后检查该舵机的插头、线缆和供电连接，再复测；必要时与已正常通讯的线缆/接口对照。现有数据不能单独确定是线缆、接触、设备还是总线时序问题。
2. **卸载保护配置。** 读到的 14 颗关节舵机寄存器 19 均为 `4`。按仓库飞特内存表，它仅设置过热保护位，未设置电压、过流和过载卸载位；本次只读取，没有修改。阈值也需结合具体型号核对，不能仅打开开关就视为保护验收通过。
3. **回零姿态与机械范围。** 数值 2048 是否对应每个关节的安全装配零位还需逐关节确认；校准偏移大不能仅凭数值判定装配错误。保护与通讯确认后，再在机体有支撑的条件下做低速、小范围验证。
4. **其他功能。** 本次 Armbian 启动没有出现 `/dev/video*`，摄像头配置/复测仍待处理。本次没有运行策略模型或机器人动作。
